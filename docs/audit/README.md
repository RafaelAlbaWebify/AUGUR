# AUGUR — Code audit: reproducible baseline

## Harness certification boundary — 2026-10-24

**Decision:** adopt the existing quality system as the mandatory *practical, bounded* engineering harness; stop expanding it without a demonstrated new regression risk. It is not a complete formal certification of every dynamic call, API schema, external provider, database migration or performance path.

**Integrated evidence:** existing `.github/workflows/ci.yml` runs the Python dependency/write-path audit, backend pytest, frontend TypeScript build + Chromium Playwright, npm dependency audit, PowerShell parser, `change_impact.py` static import and API route gate, `check_compare_contract.py` structural comparison response check, and a synthetic 29-indicator timing/memory baseline. GitHub CI was green on merged PRs #132–#138. Isolated mutation regressions detect missing TS imports, deleted API route, wrong FastAPI router prefix, missing comparison response fields, and a database connection moved ahead of batch validation. Transaction rollback/idempotence tests use disposable DuckDB fixtures, not operator data. **The last two fail-closed inputs** (removed contract file, missing frontend route-map) are exercised by this candidate PR; these are pending CI until proven.

**Measured reference (GitHub Actions CI, PR #136):** synthetic in-memory two-country/29-indicator comparison, 300 iterations: median 0.09116 ms, p95 0.09959 ms, tracemalloc peak 54,840 bytes. Not representative of complete local app latency and not a claimed optimization. No comparable before/after speedup is established.

**Explicit residual risks:** Python AST call graph and literal relative TS import graph are partial; dynamic TS imports, aliases/barrels, generated URLs, source-specific SQL, provider contracts, full response type equivalence, browser data accuracy, UI render timing, cold startup, CPU, real DB and HTTP throughput are not exhaustively tracked or benchmarked. Analyzer may produce false negatives outside declared scope; coverage of tests is not measured. The deterministic browser E2E uses mocked responses; live operator UI review is separate. These limitations must be recorded on material PRs rather than hidden as green checks.

**Required workflow:** baseline and change-impact report → identify related consumers/contracts/tests → make focused change with regression → CI checks → report actual metrics/limitations → merge only when green → validate live only when the change requires it. The existing tools are read-only except the explicitly isolated test fixtures; never run destructive probes against personal/operator databases. 


## Engineering Harness — Change Impact Gate (incremental)
AUGUR reuses `inventory.json` and this project's existing `ci.yml` rather than introducing another inventory. Before editing an existing module, run:

```bash
python backend/scripts/audit_repository_inventory.py
python backend/scripts/change_impact.py --changed-file frontend/src/components/ComparePanel.tsx
```

For a checkout with `origin/main` available, analyze the whole candidate branch:
```bash
python backend/scripts/change_impact.py --base origin/main
```
The command is **read-only**. Output reports known Python local imports/reverse importers, literal relative frontend TypeScript/JavaScript importers, explicit cross-boundary contract hints, related tests, and explicit gaps. The result is **not an exhaustive dependency graph**: TypeScript/JS dynamic calls or barrel re-exports, dynamic dispatch, SQL/DB writes, runtime external-service calls, and coverage of tests require separate review. On an ordinary PR, the existing CI now runs this analyzer and its synthetic regression tests before merging, in addition to backend pytest, frontend compile/Playwright, dependency audit and PowerShell parsing. New source files missing from the committed inventory are flagged (the inventory is refreshed on main). Neither missing tests nor uncovered edges can be treated as implicit success.

**Working rule:** for a consequential change, record affected consumer/API/storage, invariants, existing coverage and missing validation in the PR; execute contract-specific checks + CI before merge; inspect local live data separately. Synthetic analyzer tests are a harness smoke, *not* operational certification. The full master-harness objective (TS semantic graph, complete API contract mapping, controlled mutation detection and measured speed/coverage) remains OPEN. No database write or destructive check is performed by this analyzer.

## Inventory scope and rules
- Full tracked GitHub repository at audit start: **426 files**, including 13 GitHub workflow YAMLs, 101 backend scripts, 117 backend tests, 35 frontend files, 30 ingestors, 33 service files, and five DB files (directory counts, not all source-code files).
- **Actual reproducible snapshot:** 339 eligible source files, 301 Python source files and 1,553 class/function definitions; 14 workflow files and 102 scripts included in the working audit branch. Snapshot uses SHA-matched `reviewed_files` entries from `findings.json` to differentiate `verified_reviewed`, `stale_review` and `not_reviewed` states. It also resolves internal Python import dependencies and reverse importers; these are **static approximations**. Snapshot scans Python source via AST without executing imports; records function/class names, signatures, exact first/last lines, import references, called function names, byte size and SHA-256 per file. JavaScript/TypeScript, JSX, PowerShell and workflows receive path/hash metadata but need language-specific parsers for precise symbol/call inventories.
- Dependencies = static declared imports and unqualified called-name candidates; no guarantee of resolving reflection, dynamic imports, runtime invocation, TS module graph, SQL references or API consumers.
- **Source coverage %** = inventoried eligible source paths / all eligible source paths; **review coverage %** = human/assistant code-reviewed line-by-line source paths / all eligible source paths. These are different metrics. Coverage for the current static AST inventory cannot by itself be reported as line-by-line review.
- Every reviewed file must have its exact blob SHA-256, line range(s), call/dependency context, acceptance tests, finding severity, and review date in `findings.json`. If its SHA changes, prior review is stale and must be reverified before counting.

## Continuous snapshot freshness
- Every push on main affecting source, tests, workflows, CLI or the review findings regenerates the inventory with hash-based review invalidation; the bot commits an updated snapshot. Do not rely on an old inventory commit while the refresh workflow is running.
- `reviewed_file_count` and `stale_review_file_count` come from matching each audited SHA to the actual source SHA in that same snapshot, not from a manually maintained percent. The counts will fluctuate when files change until formally re-reviewed.
- `resolved_local_imports` and `imported_by` show statically resolvable Python module edges, **not** a complete runtime call graph. Frontend JS/TS, dynamically loaded modules and external services are separate review gates.
